## Four surfaces, and they are not interchangeable

ADR-008 adopted three Supabase capabilities — Postgres, Auth and Storage — and *rejected*
the Data API as the primary interface. So the surface your SvelteKit code will lean on hardest
is not A; it is B, C and D. A is enumerated for completeness.

| | A — Data API | B — Server data layer | C — Auth | D — Storage |
|---|---|---|---|---|
| Generated by | PostgREST, from the schema | us, hand-written | Supabase GoTrue | Supabase Storage |
| Reached via | `/rest/v1/*` | `load` / `actions` / `+server.ts` | `supabase.auth.*` | `supabase.storage.*` |
| Called from | browser via `supabase-js` | SvelteKit server | browser + server (`@supabase/ssr`) | server |
| Credential | user JWT + `apikey` | session cookie | — | user JWT |
| Tenant isolation | RLS via `request.jwt.claims` | RLS **plus** per-request `SET LOCAL` | n/a — auth is central (ADR-009) | bucket path + RLS |
| ADR-008 stance | *"administrative reads only"* | **primary** | adopted | adopted |

ADR-008 rejected PostgREST as the primary API for four reasons that still hold:
transactional business operations (a payroll run) span many tables; the 33 validators in
`validation-utils.js` must be the server-side authority; UC-1.1 writes eight modules in one
transaction; secrets need a server-side home. ADR-009 adds a fifth — a PostgREST URL is bound
to one Supabase project, so it cannot serve tier-B or tier-C customers whose database is
elsewhere. **Surface A is therefore enumerated below for completeness, not as a recommendation.**

Two of these deserve emphasis, because both fail *silently* rather than loudly:

- **#2** is a deadlock. The hook reads `tenant_users` to find the membership, but
  `tenant_users` carries `tenant_isolation` with no `TO` clause, so the policy applies to
  `supabase_auth_admin` too — and at token issue there is no claim yet. The hook finds nothing,
  stamps nothing, and login *succeeds*. Every query afterwards returns zero rows.
  `SECURITY DEFINER` does not fix it: under `FORCE ROW LEVEL SECURITY` the owner is subject to
  policies as well. It needs an explicit permissive policy for that one role.
- **#5** turns a missing tenant into a database error rather than an empty result. Under
  ADR-009's long-lived pools, a cleared setting is reachable, and the difference between
  "no rows" and "500" is the difference between isolation and an outage.

## Surface A — Supabase Data API (reflected)

Every table below yields the same six operations. This is the complete pattern; it is not
repeated per table because PostgREST generates it uniformly.

```http
GET    /rest/v1/<table>?select=*&<col>=eq.<val>&order=<col>&limit=&offset=   # list / filter
GET    /rest/v1/<table>?id=eq.<uuid>&select=*                               # single row
POST   /rest/v1/<table>                      Prefer: return=representation  # insert
PATCH  /rest/v1/<table>?id=eq.<uuid>                                        # update
DELETE /rest/v1/<table>?id=eq.<uuid>                                        # delete
POST   /rest/v1/<table>                      Prefer: resolution=merge-duplicates  # upsert
```

Embedded resources traverse the declared foreign keys, e.g.
`GET /rest/v1/employees?select=*,firm_departments(name),compensation_base(*)`.

## Surface B — the server data layer (what you are about to build)

ADR-004 fixes the shape: `+page.server.ts` `load` for reads, form `actions` for writes,
`+server.ts` only where a non-page consumer needs JSON, and `$lib/server/` for the SQL —
a boundary SvelteKit enforces at build time.

**Routes are not one-per-table, and the inventory below is not a route list.** A `load` runs
in the same process as the Postgres client, so ADR-004's rule is *one page, one query*: the
employee directory joins `employees`, `firm_departments` and `compensation_base` in a single
`load`. Pages are defined by `02-ux-design-specification.md` and the mockups in
`html-mockups/` — ground the route tree there when you build it.

What *is* one-per-table is the repository layer. Each table below needs exactly one
`$lib/server/<module>/<resource>.repo.ts` owning its SQL, and that is mechanically derivable,
so it is what this section enumerates.

```
src/lib/server/<module>/<resource>.repo.ts     SQL, the only place it lives   <- one per table
src/routes/(app)/<page>/+page.server.ts        load + actions                 <- one per PAGE
src/routes/api/<module>/<resource>/+server.ts  GET/POST/PATCH                 <- JSON consumers only
```

Each repository gets the canonical operations below unless a domain operation in the next
section overrides it.

## Surface D — Supabase Storage

ADR-008 adopts Storage for *"documents, attachments, exports."* No `supabase.storage` call
exists in `app/src` yet, so this surface is entirely ahead of you. It is derived from the

The client shape is the same everywhere:

### Two decisions to make before uploading anything

1. **Bucket layout.** Prefix every object path with `tenant_id` — `<bucket>/<tenant_id>/<...>` —
   so a Storage RLS policy can enforce the same isolation the tables have. Private buckets and
   signed URLs for anything employee-related; a public bucket only for logos and avatars.
2. **What the `*_url` columns store.** A signed URL expires, so persisting one gives a column
   that silently rots. Store the object *path* and mint a signed URL per request. The column
   names above say `url`, which is the wrong contract — worth correcting in the schema before
   code depends on it.

Under ADR-009, tier-B and tier-C customers have their own database but share this Storage
project. The `tenant_id` path prefix is what keeps their objects apart.
